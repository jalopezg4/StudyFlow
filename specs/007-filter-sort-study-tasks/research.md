# Research: Filter and Sort Study Tasks

## Decision 1: Filter/sort are query-string parameters on the existing `GET /api/tasks`, not a new route

- Decision: `status`, `subjectId`, `sortBy`, `sortDir` are read via `getQuery(event)` and validated by a new `TaskListQuerySchema` in `server/utils/tasks/schemas.ts`, inside the existing `handleListStudyTasks` in `server/api/tasks/index.get.ts`.
- Rationale: The spec explicitly frames this as narrowing/reordering "the existing task listing HU06 already delivers" (Assumptions), not a parallel API. A single route keeps the client contract simple (one endpoint, optional params) and avoids duplicating the auth/ownership wrapper (`requireAuthenticatedPrincipal` + `requireRequestSupabaseClient` + `executeProtectedHandler`) HU06 already established.
- Alternatives considered: A separate `GET /api/tasks/search` or `POST /api/tasks/query` route — rejected as an unnecessary parallel API the spec's Assumptions section explicitly warns against ("reuses the existing task model and APIs instead of creating a parallel one").

## Decision 2: Validate with a Zod allow-list schema *before* any Supabase call; reject the entire request on any single invalid parameter

- Decision: `TaskListQuerySchema` uses `z.enum([...])` for `status` (`pending`/`completed`), `z.enum([...])` for `sortBy` (`dueDate`/`createdAt`/`title`) and `sortDir` (`asc`/`desc`), and `z.string().uuid()` for `subjectId`. The handler runs `validateWithSchema(TaskListQuerySchema, getQuery(event), 'query')` (the existing shared helper in `server/utils/security/validation.ts`, already used for `body`/`params` sources elsewhere) first; on failure it throws `422 VALIDATION_ERROR` immediately — no partial application, no repository call happens if validation fails.
- Rationale: FR-007/FR-008/FR-013 require an explicit allow-list evaluated before any filter/sort logic runs, and reject the *whole* request (not a best-effort partial one) on any unsupported/malformed value, including the "valid filter + unsupported sort" combination case (US4 Acceptance Scenario 2). Doing this as a single schema `.safeParse()` over the whole query object — rather than checking each param independently — makes "reject everything if anything is invalid" the natural behavior instead of something to remember to enforce per-field.
- Alternatives considered: Silently drop/ignore unsupported values and apply only the recognized ones — explicitly rejected by FR-008 and the spec's edge cases (case-variant filter values, conflicting duplicate params, orphan sort direction must all be rejected, not tolerated).

## Decision 3: A repeated filter query param (e.g. `?status=pending&status=completed`) is rejected, not resolved by picking one

- Decision: Nitro's `getQuery` returns an array when a key repeats (`status: ['pending', 'completed']`). `TaskListQuerySchema`'s fields are typed as single values (`z.enum([...])`, not `z.array(...)`), so Zod naturally fails validation on an array where a string is expected, which throws the same `VALIDATION_ERROR` path as any other malformed input.
- Rationale: The spec's edge cases explicitly require rejecting duplicate-with-conflicting-values as invalid rather than "arbitrarily pick one" (first or last). Relying on Zod's default type mismatch (array where string/enum expected) gets this for free with no extra branching logic.
- Alternatives considered: Explicitly detect arrays and throw a custom message — rejected as unnecessary; the generic validation error is sufficient and consistent with how every other malformed-input case in this schema is handled.

## Decision 4: Subject-filter ownership is enforced by the existing `user_id` scoping, not a second lookup

- Decision: `subjectId` is validated only for well-formedness (`uuid`). No separate "does this student own this subject" query is added. `listStudyTasksForOwner` applies `.eq('user_id', userId)` (unchanged from HU06) together with `.eq('subject_id', filter.subjectId)` when supplied.
- Rationale: `CreateStudyTaskSchema`/`createStudyTask` (HU05) only ever creates a task whose `subject_id` belongs to the same `user_id` that owns the task (subject ownership was already checked at creation time — see `specs/005-create-study-task`). Consequently, for any task where `user_id = <requesting student>`, `subject_id` can only ever be a subject that same student owns. Filtering by a `subjectId` the student doesn't own can therefore never match any of their own tasks — the `AND user_id = :me AND subject_id = :filter` combination yields an empty result automatically, satisfying FR-009's "syntactically valid subject identifier the student does not own MUST yield an empty result rather than another student's data or an error revealing that subject's existence" without any extra query, extra round trip, or subject-existence check that could itself leak information.
- Alternatives considered: Look up the subject first and verify `subjects.user_id = principal.userId` before filtering — rejected as redundant work that adds a second query and a second place ownership logic could drift from the task table's own guarantee, for a case the existing data model already closes structurally.

## Decision 5: Sort criteria map to explicit `.order()` calls from a fixed allow-list; direction requires a criterion

- Decision: A `sortBy → column` map (`dueDate → due_date`, `createdAt → created_at`, `title → title`) is defined as a `Record`, indexed only by the validated enum value — never by a raw string. `sortDir` without `sortBy` is rejected by a Zod `.refine()` on the whole query object (mirroring `UpdateStudyTaskSchema`'s "at least one of..." refinement pattern from HU06). `sortBy` without `sortDir` uses a per-criterion default direction: `dueDate → asc` (soonest first, matching the user story's "surface what's due soonest" goal), `createdAt → desc` (matches HU06's existing default order), `title → asc` (alphabetical).
- Rationale: FR-013 requires sort ordering to come exclusively from allow-listed values, never unvalidated client input reaching `.order()`; indexing a fixed `Record` by an already-validated enum makes constructing an arbitrary/unsafe column name structurally impossible (there is no code path from raw query string to `.order(columnName)`). The edge case "direction alone, no criterion, is meaningless and must be rejected" is explicit in the spec.
- Alternatives considered: Always require both `sortBy` and `sortDir` together (no defaults) — rejected as unnecessarily strict; the spec only requires rejecting a lone direction, not a lone criterion, and per-criterion defaults keep the common case (`?sortBy=dueDate`) ergonomic.

## Decision 6: Deterministic tiebreaker via a secondary `.order('id', ...)` on every query

- Decision: Every listing query appends `.order('id', { ascending: true })` as a final secondary sort key, after the primary (`due_date`/`created_at`/`title`, or the HU06 default `created_at desc`) is applied.
- Rationale: FR-012 requires a documented, deterministic tiebreaker for any two tasks equal on the active sort criterion (e.g., same due date, or two tasks with no due date at all — `due_date IS NULL` ties are common). `id` (a UUID primary key) is unique per row and never null, so it is a total order over any residual ties regardless of which primary criterion is active — including the no-params default case, which also gains this same tiebreaker (a harmless strengthening of HU06's existing "most recently created first" behavior, not a behavior change to it, since `created_at` collisions were already an unspecified tie in HU06).
- Alternatives considered: Use a compound tiebreaker like `created_at` as the secondary key when the primary is `dueDate`/`title` — rejected; `created_at` (timestamptz) could theoretically still collide, whereas `id` cannot, and a single uniform tiebreaker column is simpler to document and test than a per-criterion tiebreaker table.

## Decision 7: Reuse HU06's default listing behavior unchanged when no filter/sort params are supplied

- Decision: `listStudyTasksForOwner(supabase, userId)` (no filter/sort arguments) continues to produce exactly HU06's existing query — `.eq('user_id', userId).order('created_at', { ascending: false })` — with only the new `.order('id', { ascending: true })` tiebreaker from Decision 6 added. The route parses `getQuery(event)` and passes `undefined` filter/sort through when the query string is empty, rather than substituting synthetic default values that happen to produce the same SQL.
- Rationale: FR-011 requires the no-params case to be identical to HU06's already-established default. Treating "no params" as "call the function the same way HU06 always called it, plus one additive tiebreaker" keeps this a strict extension rather than a reimplementation that could silently drift from HU06's behavior.
- Alternatives considered: Always run params through the full filter/sort object with defaults filled in — rejected; it is extra indirection for no behavioral gain, and defaults-filled-in and "actually no params" are not exactly the same code path to reason about later.

## Decision 8: No UI filter/sort controls in this iteration

- Decision: This plan ships the `GET /api/tasks` query-parameter contract only. `TaskList.vue` (HU06) is not modified.
- Rationale: The spec's User Scenarios, Functional Requirements, and Success Criteria are written entirely in terms of "the response"/"the request" — a listing API contract — with no acceptance scenario mentioning a filter/sort UI control. Every prior HU in this codebase (HU05, HU06) shipped backend-first with UI as a co-requirement only when the spec's acceptance scenarios were UI-observable; here they're API-observable. Adding UI now would be scope not requested by this spec.
- Alternatives considered: Add filter dropdowns/sort controls to `TaskList.vue` in the same PR — deferred; can be scoped as fast, low-risk follow-up UI work once this contract exists, without blocking this feature's own acceptance criteria.
