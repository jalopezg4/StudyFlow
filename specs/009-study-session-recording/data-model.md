# Data Model: Study Session Recording

## Entity: Study Session

A persisted record of time a student dedicates to studying.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID | Yes | Primary key, generated by the database |
| `user_id` | UUID | Yes | References the authenticated owner; never accepted from request input |
| `subject_id` | UUID | Yes | References an owned subject; deletion follows the existing subject lifecycle decision |
| `task_id` | UUID | No | Optional reference to an owned task under the same subject |
| `duration_minutes` | Integer | Yes | Whole number from 1 through 1,440 |
| `created_at` | Timestamp | Yes | Generated by the database; not client-controlled |

## Relationships

- One authenticated student owns many study sessions.
- One subject can contextualize many study sessions.
- One study task can be associated with many study sessions.
- If `task_id` is present, `study_tasks.subject_id` MUST equal `study_sessions.subject_id` and both resources MUST belong to the authenticated student.

## Integrity and Authorization Rules

- Study sessions are user-owned and protected by Supabase RLS.
- The API derives `user_id` from the authenticated principal.
- The API validates the subject owner before insertion.
- The API validates the optional task owner and same-subject relationship before insertion.
- Invalid or unauthorized references must not create a session.
- Subject/task deletion behavior must be made explicit in the migration and verified in the quickstart; the initial implementation should cascade session history with the referenced resource to avoid orphaned records or blocked existing deletion workflows.
